1. Executive summary

The problem

During an incident, on-call engineers jump between logs, deployment history, dashboards, runbooks and old postmortems while the clock runs. AI assistants can help, but one that invents log lines, cites nothing or changes production is worse than none.

The approach

ResolveAI pulls the evidence for one incident into a single workflow and asks Claude to reason only over that evidence. Three rules shape the design:

  • Evidence first. Code gathers the evidence and picks similar past incidents. Every record gets a typed ID, and the server removes any citation it can't match to a real record.
  • Read-only by construction. Each system sits behind its own MCP server with fixed, parameterised checks. No tool runs arbitrary SQL or shell commands.
  • A person decides. Output is labelled as a draft, checks are recommendations, and an incident stays in a review queue until someone records a verified cause and reviews the RCA.

Current status

Working today

  • Blazor Server UI and HTTP API on one ASP.NET Core app
  • Full investigation pipeline in recorded mode
  • Four read-only MCP servers, with 17 tools, including real SQL Server checks
  • RCA drafting, editing, versioning and Markdown export
  • 205 automated tests, plus a Docker image

Not done or not proven

  • Live Claude has never run against the real API. It is only tested against a fake API.
  • Data is synthetic, apart from optional SQL Server checks
  • No user accounts; a shared access code gates paid runs
  • CI workflow has not yet run on GitHub
  • Single process, with SQLite

2. Architecture

2.1 System context

ResolveAI sits between an on-call engineer and the systems they would otherwise check by hand. It only reads from those systems, and only calls out to Claude in live mode.

2.2 Containers and processes

One ASP.NET Core process serves both the UI and the API. It starts one child process per system when it boots and talks to each over MCP on stdio.

3. Workflows

3.1 Investigation, end to end

Starting a run returns HTTP 202 at once and the work continues on a background task. Each stage's timing and counts are stored as a trace, shown in the UI as How this was produced. The UI polls every 1.5 seconds.

3.2 Live follow-up loop

This is what lets Claude ask further questions of the systems. The SDK tool runner drives the loop, but every call passes through ResolveAI's callback, which records it and enforces the limit. The model can't exceed it, because past the limit it only receives a refusal.

4. Components

4.1 Evidence gathering

Pipeline/EvidenceLoader.cs is deterministic and involves no model. For one incident it loads:

  • Logs: the affected service, or linked to the incident, from 30 minutes before the start to one hour after detection, up to 200 rows.
  • Deployments: the same service in the 48 hours before, and other services within one hour either side.
  • Also: metric snapshots, timeline events, and up to five runbooks or guides, plus error signals counted from the logs by signature.

4.2 Similar incidents

Pipeline/Similar.cs builds search terms from the title, description, error signatures and same-service change summaries, then runs an FTS5 query. The model never chooses candidates; it can only explain them.

score = -bm25 x 10 + matched terms + (3 if same service)
keep   candidates with at least 2 matched terms, and at least 35% of the best score, up to 5

4.3 Evidence packet

Pipeline/Packet.cs builds the only thing the model is allowed to see. Each item has a typed ID that the validator later checks citations against.

PrefixSourcePrefixSource
log:Log groupdoc:Runbook or guide
dep:Deploymenthist:Past incident
met:Metric snapshottl:Timeline event
mcp:NSystem check result
  • Deduplication: log lines differing only by IDs or numbers collapse into one group with a count.
  • Bounds: 40 log groups, preferring errors and warnings; excerpts of 600 characters, or 1,200 for tool results; 40,000 characters in total, dropping information logs first.
  • Ordering: by time, with tool results last in call order.

4.4 Redaction

Pipeline/Sanitizer.cs runs when the packet is built. Stored logs and tool rows aren't changed, so an engineer still sees the raw record, and a database trigger rejects any update to log rows. It redacts URL credentials, Bearer and Basic values, provider-style keys (sk_, sk-ant-, AKIA, ghp_), key=value secrets, email addresses and card-like numbers.

Limitation: these are patterns. A secret in an unusual format can pass through, which matters most once real data is sent to a cloud model.

4.5 Validation

Pipeline/Validate.cs enforces what a JSON schema can't express, because model output is treated as untrusted.

CheckBehaviour
CitationsAny ID not in the packet is removed and noted. A hypothesis left with none is marked speculative and forced to low confidence.
Unsafe checksRecommended checks describing destructive actions (rm -rf, kubectl delete, DROP TABLE, terraform destroy and similar) are removed.
Invented numbersNumbers with a unit, or of 10 or more, that don't appear in the evidence are flagged, not deleted, so a person decides.
Similar incidentsExplanations for anything outside the retrieved candidates are ignored.
Bounds5 hypotheses, 8 list items, 5 checks, and clipped text lengths.
Ranking2 x confidence (1, 2 or 3) + min(citations, 5) - counter-evidence. For ordering only; never shown as a probability.

4.6 LLM providers

RecordedProvider (default)

No network. INC-1042, INC-1045 and INC-1046 replay written analyses, which adapt to the checks that actually ran. Other incidents get a rule-based analysis built from the packet. Output goes through the same validation as live output.

ClaudeProvider (live)

Analysis: effort medium, 16,000 tokens, structured output, fallbacks: "default". Follow-ups: effort low, 4,000 tokens, through the tool runner. Replies are also checked for shape and valid confidence values before use. Refusals, cut-offs and API errors become readable messages.

4.7 MCP hub

Mcp/Hub.cs starts each enabled server, keeps only tools marked readOnlyHint, routes calls, and restarts a crashed server once. A system that fails to start shows as Not working and never stops the app. Mcp/Baseline.cs decides the fixed checks for each incident from mcp.config.json: database checks if the service has a database, error and warning searches of its log folders, recent deployments and its key metrics.

6. Data model and API

6.1 Data model

There are 14 tables, two FTS5 search tables and a _migrations table. IDs are UUID strings, and seeded IDs are derived from stable names, so recorded analyses can cite them and resets produce identical data.

JSON columns: lists and structured values are stored as JSON text, such as evidence_packet, trace, limitations, recommended_checks and rows. The stored packet is the permanent record of exactly what the model saw.

Migrations: SQL files embedded in the app and applied in filename order, each in a transaction, and recorded by filename.

6.2 HTTP API

JSON uses snake_case. Errors are { "error": "message" }. :id on incidents accepts a UUID or a key such as INC-1042.

7. Design decisions

Each record gives the decision, the reasoning, what was rejected, and what it costs.

D1. Code gathers evidence; the model only reasons over it

Why: a model that searches freely can miss evidence or be steered by injected text, and its results are hard to audit. Rejected: a fully agentic investigation. Cost: baseline checks are fixed, so unusual incidents depend on follow-ups.

D2. One read-only MCP server per system, with fixed tools

Why: a separate process per system gives a clear boundary, independent failure and reuse from other MCP clients, and safety that doesn't depend on model behaviour. Rejected: a generic "run SQL" or "run command" tool, which would be more flexible but unsafe. Cost: each new question needs a new tool.

D3. Enforce read-only in the target system too

Why: running queries as resolveai_reader means SQL Server refuses writes even if the code has a bug or connects as an admin. Cost: setup needs an administrator once, and the login needs specific grants.

D4. Validate model output on the server

Why: structured output guarantees shape, not truth. Rejected: trusting citations, or deleting flagged text outright; flagged numbers are kept so a person decides. Cost: permissive matching means a number appearing anywhere in the evidence counts as verified.

D5. Similar incidents are retrieved by code

Why: deterministic and testable, and the model can't invent a precedent. Rejected: vector search, which adds infrastructure not justified at this scale. Cost: keyword search misses matches phrased differently.

D6. Recorded mode as the default

Why: demos and tests behave the same every time, with no cost or network. Cost: it can look more finished than it is: recorded analyses were written by hand and prove the pipeline, not the model's judgement.

D7. Blazor Server, with the UI and API sharing AppService

Why: one language and no client-side secrets, and rules that sat in route handlers moved to one place so the UI can't bypass them. Rejected: a Blazor UI calling the API over HTTP, which adds a hop in the same process. Cost: each user holds a live server connection, so scaling out would need sticky sessions.

D8. Port from Node against recorded golden files

Why: the highest risk was silent change, such as weakened redaction or different scoring. Recording every route, investigation, prompt and tool result first made differences into test failures. Cost: intentional behaviour changes now require updating the golden files.

D9. Pin the MCP protocol version

Why: an unpinned client probes for a newer version on a short timeout, then falls back to a handshake that a slow-starting server refuses. That made systems randomly fail on a busy machine, in about 40% of parallel test runs. ResolveAI ships both ends, so nothing needs negotiating. Cost: newer protocol features need a deliberate change.

D10. SQLite

Why: anyone can run the project from the README with no database setup, and FTS5 is enough at this scale. Cost: limited to one server; Part B replaces it.

D11. Store evidence as JSON on the investigation

Why: an investigation stays reproducible and auditable even after source data changes. Cost: large rows, and queries can't easily reach inside them.

8. Security and threat model

8.1 Assets and trust boundaries

The main assets are incident evidence (which can contain secrets and personal data), credentials (API key, SQL login, access code), the integrity of monitored systems, and the paid API budget.

8.2 Threats and mitigations

8.3 Known gaps

  • No user accounts. Safety relies on binding to localhost. Anyone reaching the port can read everything and run recorded investigations.
  • No cross-site protection on the HTTP API. A web page you visit could send a request to it on localhost, including POST /api/demo/reset, which erases investigations. Set DEMO_MODE=false where that matters.
  • No DNS-rebinding protection. The Origin check compares against the Host header, and allowed hosts aren't restricted.
  • Pattern-based redaction can miss secrets. Raw rows are shown to anyone using the app, by design.
  • No audit log of who did what, because there are no identities.

9. Deployment and operations

9.1 Local

dotnet run --project src/ResolveAI.App      # http://localhost:8787

Requires the .NET 10 SDK. An empty database is seeded on first start. Settings come from .env if present, and real environment variables win over the file.

9.2 Container

cp .env.example .env              # optional, for live runs
docker compose up -d --build
docker compose ps                 # wait for "healthy"
  • Image: published app on dotnet/aspnet:10.0, non-root, no Node. The app is its own health check (--healthcheck), since the image has no curl.
  • Network: published on 127.0.0.1 only. Compose sets DEMO_RESET_ANY_IP=true, because callers arrive from the bridge network; this is safe only with that loopback binding.
  • Data: SQLite on the named volume resolveai-data.
  • SQL Server from Docker: use the tedious driver setting with a SQL login, as Windows sign-in isn't available.

9.3 Configuring systems

mcp.config.json, or the committed example if it's absent, maps each service to log folders, a git repository, a database and key metrics, and sets allowed folders. Relative paths resolve against the file's folder. Secrets stay in .env.

sqlcmd -S localhost -E -C -i demo-systems/sqlserver/setup.sql
# then: "sqlserver": { "enabled": true, "driver": "msnodesqlv8", "execute_as": "resolveai_reader" }

Both driver names now use Microsoft.Data.SqlClient; they are kept so that existing config files stay valid.

tests/ResolveAI.Tests/Golden holds what the Node implementation returned. Comparisons normalise only what legitimately varies: random IDs, current times, file modified times and sizes, and durations. 10.3 Bugs this strategy found

Each of these passed in-process tests and only failed under more realistic conditions, which is why several layers exist:

  • All MCP servers crashed at launch from the app's folder (found by running the published app).
  • Blank page in the container, because restore ran before the source was copied (found by testing the image).
  • Random startup failures from MCP version negotiation (found by running projects in parallel).
  • The database code was never committed, because .gitignore matched it on Windows (found by testing a fresh clone).

12. Roadmap

The phases are ordered so that the riskiest assumption is tested first: if live analysis isn't useful, the rest isn't worth building. There are no dates or effort estimates, because those depend on team size. Each phase has an exit condition that can be checked.

13. Target architecture

This part is a plan. None of it is built or tested. It records the direction chosen for an on-premises deployment, so that reviewers and adopters can assess it. Products are named as integration options, and their details should be confirmed at design time for each phase.

13.1 Overview and hosting

ResolveAI runs on one Windows Server inside the company network, using the existing Windows, Active Directory and SQL Server skills of an on-premises team.

TopicDesign
HostASP.NET Core under IIS or as a Windows service, on HTTPS with a company certificate. IIS needs its WebSocket feature enabled for Blazor.
Service accountA dedicated low-privilege account, ideally a group managed service account. MCP servers run as children under it, with the same minimal environment as today.
SecretsStored outside source and config, for example in environment settings protected by Windows DPAPI or a company vault, and readable only by the service account.
Data protection keysPersisted to a protected folder, so sessions survive restarts.

13.4 Model access

Claude can't run on-premises, so live analysis sends evidence outside the network. Each site chooses a route in configuration, behind the existing ILlmProvider layer. The rest of the pipeline doesn't change.

RouteHow it worksSuits
A. Direct APIHTTPS to the Claude API through the company proxy, with one allow-listed destination.Sites allowing controlled outbound access; simplest
B. Private linkClaude through Amazon Bedrock or Microsoft Foundry over a private connection, under the company's cloud contract.Sites requiring no public internet path
OffNo model calls. Rule-based analysis only, with all evidence gathering still working.Sites not yet approved

Controls on every route: redaction before anything leaves; an audit record of each packet sent; live mode allowed per service, so sensitive ones can stay off; the daily limit; and automatic fallback to recorded mode with a clear label.

Design points for route B: the C# SDK has dedicated clients for these platforms, and model IDs can differ. The fallbacks: "default" setting used today isn't available on Bedrock or Foundry, so refusal handling needs the SDK's client-side fallback instead. Availability of each feature must be confirmed per platform and tested, since structured output and the tool runner are both relied upon.
Decision each site must make: redaction is pattern-based, so some sensitive content can leave the network. This should be an explicit, recorded approval by the site's security owner, not a default.

13.5 Evidence sources

Every source follows the same pattern as today: its own read-only MCP server, fixed tools, the same limits, and its results become cited evidence. File logs already work through the existing files server, by adding folders to its allow-list.

CategoryOptionsPurpose and notes
Incident toolsServiceNow, Jira Service Management, PagerDutyImport real incidents to replace the demo seed. Read-only: ResolveAI never updates tickets.

Other systemsMessage queues, Kubernetes, feature flags, HTTP probesAdded through the checklist below.

Checklist for adding any system

  1. Use a read-only credential, so the source system enforces the guarantee itself.
  2. Provide fixed, parameterised tools, never a free-form query or command.
  3. Apply the standard limits: time window, rows, output size and timeout.
  4. Treat its output as untrusted, and confirm that redaction covers its formats.
  5. Add attack tests for every input a caller controls, and a test against a fake source.
  6. Add its baseline checks, and show that it improves investigations before keeping it.

13.6 Operations

AreaPlan
MonitoringHealth endpoint, MCP server status, run failures, model errors, spend against the limit, fed to the company's monitoring through OpenTelemetry or Windows event logs.
LoggingStructured application logs, without evidence content or secrets.
BackupStandard SQL Server backups, plus configuration and protected keys. Recovery targets are set by the site, and restores are rehearsed.
PatchingA scheduled window, with a maintenance notice. Migrations apply at startup, after a backup.
CapacityEach user holds a live connection and each run uses background work. To be measured in the pilot; the design expects tens of users, not thousands.

What choosing a single server accepts

  • Downtime during patching or a server failure, until it is restored.
  • Investigations in progress are lost on restart, and are marked failed to be run again.
  • Users reconnect after a restart.

This is reasonable because ResolveAI supports incident response but isn't part of the production path: engineers can still investigate by hand while it's down. If it became critical, the next step would be a second server, which needs sticky sessions, shared keys, and investigations moved to a database-backed queue.

13.7 Open questions

These can only be settled with a real deployment:

  • What accuracy from the evaluation in phase 1 is good enough to continue?
  • Which incident tool does the first pilot use, and how are its services mapped to log folders, databases and metrics?
  • Which route does the first site approve, and what must be redacted beyond today's patterns?
  • How long may investigations and evidence packets be retained?
  • IIS or Windows service, given the site's standards?
  • What budget should the daily live limit reflect, once phase 1 has measured the cost?
